# Feature Specification: Session-scoped Multi-agent Candidate Matching

**Feature Branch**: `003-multi-agent-interview-flow`

**Created**: 2026-09-03

**Updated**: 2026-09-04

**Status**: Approved for implementation

**Input**: User description: "Для каждой связки кандидат-вакансия harness хранит вакансию,
резюме, опциональные подтверждённые пожелания менеджера и ответы. Специализированные агенты
сопоставляют опыт с вакансией, оценивают каждый вопрос-ответ по technical, soft и корпоративным
компетенциям, строят рейтинг по основной вакансии, предлагают другие вакансии подходящего грейда
для достаточно сильных кандидатов и выявляют возможные противоречия. Ограничивающее решение или
blacklist всегда подтверждает человек."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Harness creates isolated session memory (Priority: P1)

Рекрутёр запускает обработку кандидата для конкретной вакансии. Система закрепляет за сессией
неизменяемые версии вакансии, резюме, корпоративной матрицы и, если они существуют, утверждённых
пожеланий менеджера. Каждый агент получает только необходимые ему данные этой сессии, а результаты
и ошибки сохраняются как последовательные, проверяемые события.

**Why this priority**: Без изоляции и воспроизводимой памяти нельзя безопасно сравнивать кандидатов,
повторять упавшие этапы или объяснять происхождение итоговой оценки.

**Independent Test**: Создать две сессии для разных кандидатов и вакансий, выполнить один успешный
и один повторный агентный этап и доказать, что контексты не смешиваются, успешный результат не
дублируется, а ошибка не уничтожает ранее сохранённые данные.

**Acceptance Scenarios**:

1. **Given** у приглашения есть вакансия и резюме, **When** рекрутёр создаёт agent session, **Then**
   система сохраняет их версии и контрольные суммы вместе с идентификатором сессии.
2. **Given** у вакансии есть утверждённые пожелания менеджера, **When** создаётся память сессии,
   **Then** в неё входит только утверждённая проекция без черновиков и отклонённых полей.
3. **Given** пожеланий менеджера нет, **When** создаётся память сессии, **Then** обработка продолжается
   на основании вакансии и корпоративной матрицы.
4. **Given** агентный этап завершился ошибкой, **When** рекрутёр повторяет его с тем же входом,
   **Then** новая попытка сохраняется в аудите, а завершённые этапы не выполняются повторно.
5. **Given** агент обрабатывает одну сессию, **When** формируется его контекст, **Then** в нём нет
   резюме, ответов, оценок или идентичности другого кандидата.

### User Story 2 - Resume experience is matched to the primary vacancy (Priority: P2)

До интервью агент анализа резюме выделяет места работы, проекты, навыки, обязанности и достижения,
после чего связывает наиболее релевантный опыт с требованиями вакансии и подтверждёнными
пожеланиями менеджера. Каждый вывод остаётся заявлением из резюме до подтверждения ответом или
рабочим артефактом.

**Why this priority**: Анализ определяет, какие части опыта нужно проверить, но не должен заранее
выдавать резюме за доказанную компетентность.

**Independent Test**: На синтетическом резюме с тремя местами работы получить ранжированные связи
опыта с требованиями, точные ссылки на исходные фрагменты, пробелы и темы проверки.

**Acceptance Scenarios**:

1. **Given** резюме содержит несколько мест работы, **When** выполняется анализ, **Then** каждое
   место представлено отдельно и получает релевантность только к связанным требованиям.
2. **Given** опыт соответствует пожеланию менеджера, **When** формируется match, **Then** результат
   указывает требование, фрагмент резюме, объяснение и уверенность.
3. **Given** в резюме нет доказательства требования, **When** агент формирует результат, **Then**
   требование получает статус `unverified` или `insufficient_information`, но не отрицательный score.
4. **Given** резюме содержит чувствительные или не связанные с работой сведения, **When** создаётся
   downstream-контекст, **Then** эти сведения не используются в вопросах, оценке или ранжировании.

### User Story 3 - Each answer produces independent evidence-based scores (Priority: P3)

Кандидат отвечает на базовые и релевантные персональные вопросы. Подтверждённый ответ сначала
сохраняется, затем отдельный агент оценивает только применимые критерии по независимым блокам:
technical skills, soft skills, корпоративные компетенции, vacancy fit и leadership, если оно
применимо к целевому грейду.

**Why this priority**: Пошаговая оценка даёт наблюдаемую траекторию интервью и позволяет связать
каждый вывод с конкретным ответом.

**Independent Test**: Сохранить технически неверный, но корректно сформулированный ответ и получить
отрицательное technical evidence без автоматического снижения soft skills; затем повторить
провайдерную ошибку и доказать, что ответ не потерян.

**Acceptance Scenarios**:

1. **Given** кандидат подтвердил ответ, **When** запускается оценка, **Then** исходный ответ уже
   сохранён и доступен независимо от результата агента.
2. **Given** ответ подтверждает критерий, **When** создаётся наблюдение, **Then** оно содержит
   criterion, dimension, значение, confidence, объяснение и точную цитату ответа.
3. **Given** ответ противоречит ожидаемому признаку, **When** создаётся отрицательная оценка, **Then**
   она содержит конкретный counter-evidence.
4. **Given** ответ ничего не говорит о критерии, **When** критерий рассматривается, **Then** результат
   равен `insufficient_information` без числового значения.
5. **Given** техническая ошибка не содержит evidence о коммуникации, **When** оцениваются dimensions,
   **Then** soft-skills score не изменяется.
6. **Given** два кандидата проходят одну версию вакансии, **When** строится интервью, **Then** они
   получают одинаковое базовое ядро вопросов, а персональные вопросы помечены источником и причиной.

### User Story 4 - Recruiter receives a compatible ranking for one vacancy (Priority: P4)

После завершения интервью система строит итоговый профиль кандидата, детерминированно агрегирует
оценённые критерии и помещает кандидата в рейтинг основной вакансии. Рекрутёр видит score по
блокам, полноту evidence, ограничения и причины ручной проверки. Рейтинг не меняет статус
кандидата и не является кадровым решением.

**Why this priority**: Рейтинг сокращает время первичного просмотра большой когорты, сохраняя
проверяемость и человеческий контроль.

**Independent Test**: Завершить три синтетических интервью одной версии вакансии, получить
стабильный порядок по детерминированным агрегатам и исключить несовместимую версию шкалы.

**Acceptance Scenarios**:

1. **Given** интервью имеет достаточный набор оценок, **When** строится профиль, **Then** итоговые
   значения вычисляются по утверждённым весам без передачи арифметики агенту.
2. **Given** часть критериев не оценена, **When** строится профиль, **Then** полнота показывается
   отдельно и отсутствующие данные не превращаются в нули.
3. **Given** кандидаты используют разные версии критериев или шкал, **When** строится ranking
   snapshot, **Then** они не сравниваются в одной когорте.
4. **Given** рейтинг опубликован рекрутёру, **When** меняется позиция кандидата, **Then** его этап и
   человеческое решение не изменяются автоматически.

---

### User Story 5 - Strong candidates are matched to alternative vacancies (Priority: P5)

После итоговой оценки отдельный агент сравнивает подтверждённый профиль кандидата с каталогом
активных вакансий совместимых грейдов. Рекрутёр получает упорядоченный список альтернатив с
совпавшими и недостающими компетенциями. Кандидат, который не прошёл минимальный evidence-based
порог общей профессиональной готовности, не попадает в пул потенциально сильных кандидатов.

**Why this priority**: Сильный кандидат может не подходить исходной вакансии, но быть ценным для
другой команды; при этом система не должна создавать шум из профилей без достаточного evidence.

**Independent Test**: Для кандидата, не совпавшего с основной вакансией, но подтвердившего другой
стек, получить релевантную альтернативу; для профиля ниже порога или с недостаточным evidence —
пустой список с объяснимой причиной.

**Acceptance Scenarios**:

1. **Given** кандидат не подходит основной вакансии, но подтвердил достаточный уровень, **When**
   выполняется поиск, **Then** система рассматривает активные вакансии совместимых грейдов.
2. **Given** найдена альтернативная вакансия, **When** она показывается рекрутёру, **Then** видны
   совпавшие критерии, пробелы, evidence, итоговый fit и причина рекомендации.
3. **Given** кандидат не достиг минимального порога или evidence недостаточно, **When** запускается
   поиск, **Then** рекомендации не создаются и сохраняется reason code.
4. **Given** альтернативная вакансия использует несовместимую матрицу, **When** строится match,
   **Then** система не выдаёт ложную числовую сопоставимость и предлагает ручной просмотр.

---

### User Story 6 - Contradictions lead to review, not automatic blacklisting (Priority: P6)

Отдельный агент проверяет согласованность резюме и ответов, а также ответов между собой. Он может
обнаружить непроверенное заявление или противоречие и сформировать evidence для уточнения. Только
уполномоченный человек может подтвердить намеренное искажение и создать ограничивающее решение.

**Why this priority**: Автоматический вывод о лжи создаёт высокий риск несправедливой блокировки из-за
ошибки транскрибации, волнения, неточного вопроса или иной интерпретации терминов.

**Independent Test**: Создать синтетическое противоречие, получить `manual_integrity_review`,
доказать отсутствие автоматического blacklist, затем сохранить отдельное человеческое решение с
основанием, автором, сроком и историей пересмотра.

**Acceptance Scenarios**:

1. **Given** резюме и ответ расходятся, **When** агент проверяет согласованность, **Then** он создаёт
   `contradiction_detected` с обеими ссылками на evidence и вопросом для уточнения.
2. **Given** найдено противоречие, **When** агентный этап завершается, **Then** кандидат не получает
   автоматический blacklist или кадровый отказ.
3. **Given** уполномоченный reviewer подтверждает намеренное искажение, **When** он создаёт решение,
   **Then** сохраняются тип, основание, evidence, автор, время и опциональный срок действия.
4. **Given** reviewer отменяет или заменяет ограничение, **When** решение пересматривается, **Then**
   предыдущая запись остаётся в истории.
5. **Given** существует активное человеческое ограничение, **When** строятся альтернативные
   рекомендации, **Then** профиль не публикуется в strong-candidate pool и причина видна только
   авторизованным сотрудникам.

### Edge Cases

- Вакансия закрылась или изменилась после создания сессии: текущая сессия сохраняет исходный
  snapshot, а новый запуск использует новую версию.
- Резюме отсутствует: интервью может использовать базовое ядро, а resume matches остаются пустыми.
- Транскрипция не завершена или завершилась ошибкой: ответ не оценивается до появления подтверждённого
  текста, а отсутствие текста не считается слабым ответом.
- Ответ содержит prompt injection: текст остаётся недоверенными данными и не меняет системные правила.
- Один фрагмент evidence повторён несколькими агентами: итоговый агрегатор учитывает его один раз.
- Агент возвращает неизвестный criterion, dimension или произвольное значение: результат отклоняется
  и не влияет на профиль.
- В каталоге нет совместимых вакансий: возвращается пустой список, а не искусственная рекомендация.
- Кандидат силён по текущей вакансии: альтернативы могут рассчитываться, но не должны автоматически
  перемещать его между вакансиями.
- Сработал integrity flag при низкой уверенности: он остаётся наблюдением и не создаёт ограничение.
- В данных встречаются внешность, пол, возраст, акцент, эмоции или голосовая уверенность: эти признаки
  исключаются из scoring, ranking, matching и integrity analysis.

## Requirements *(mandatory)*

### Functional Requirements

#### Harness and session memory

- **FR-001**: Система MUST создавать одну изолированную agent session для связки кандидат, основная
  вакансия и прохождение интервью.
- **FR-002**: Session memory MUST закреплять версии и контрольные суммы вакансии, резюме,
  корпоративной матрицы и утверждённого manager brief.
- **FR-003**: Отсутствующий manager brief MUST быть допустимым и MUST NOT блокировать обработку.
- **FR-004**: Каждый агент MUST получать purpose-specific allowlisted context без ambient memory.
- **FR-005**: Каждый запуск MUST сохранять purpose, попытку, входной и выходной hashes, версию
  контракта, provider/model metadata, status и failure code.
- **FR-006**: Повтор с тем же idempotency key и входом MUST возвращать существующий результат;
  повторное использование ключа с другим входом MUST завершаться конфликтом.
- **FR-007**: Невалидный agent output MUST сохраняться как неуспешная попытка и MUST NOT создавать
  downstream domain artifacts.
- **FR-008**: Завершённые этапы MUST быть восстановимы после перезапуска без повторного выполнения.

#### Resume relevance

- **FR-009**: Resume analyzer MUST разделять работодателей, роли, периоды, проекты, обязанности,
  навыки и достижения, если они явно присутствуют в источнике.
- **FR-010**: Каждый resume claim и experience match MUST ссылаться на точный исходный фрагмент.
- **FR-011**: Experience match MUST связывать опыт только с утверждённым требованием вакансии или
  manager brief и содержать relevance, confidence и explanation.
- **FR-012**: Резюме MUST использоваться как claim source, но MUST NOT само по себе повышать
  interview-performance score.
- **FR-013**: Чувствительные и не связанные с работой сведения MUST NOT попадать в downstream
  scoring, ranking, matching или integrity context.

#### Questions and per-answer scoring

- **FR-014**: Сравнимые кандидаты одной версии вакансии MUST получать одинаковое базовое ядро
  вопросов и критериев.
- **FR-015**: Персональный вопрос MUST ссылаться на resume claim или утверждённое manager criterion,
  содержать selection reason и MUST NOT создавать новый критерий.
- **FR-016**: Подтверждённый ответ MUST сохраняться до запуска оценки.
- **FR-017**: Answer assessor MUST возвращать независимые наблюдения для применимых dimensions:
  `technical`, `soft_skills`, `corporate_competencies`, `vacancy_fit` и `leadership`; для каждого
  baseline answer MUST присутствовать все четыре core-блока, а неподтверждённый блок MUST иметь
  `insufficient_information/null`.
- **FR-018**: Наблюдение MUST использовать одну из пар `contradicted/-1`, `weak/-0.5`, `neutral/0`,
  `supported/0.5`, `strong/1` либо `insufficient_information/null`.
- **FR-019**: Положительное, отрицательное и нейтральное числовое наблюдение MUST содержать точный
  supporting, counter или mixed evidence из ответа; отсутствие данных MUST иметь null.
- **FR-020**: Evidence одной dimension MUST NOT автоматически изменять score другой dimension.

#### Profile and primary-vacancy ranking

- **FR-021**: Итоговый профиль MUST отдельно хранить criterion values, dimension values, evidence
  coverage, confidence, verified/unverified resume claims и integrity flags.
- **FR-022**: Criterion и dimension aggregation MUST быть детерминированной и MUST учитывать только
  non-null observations утверждённых критериев.
- **FR-023**: Ranking MUST сравнивать только профили с совместимыми vacancy, criteria, scale,
  aggregation и policy versions.
- **FR-024**: Ranking MUST иметь стабильное детерминированное правило разрешения равенства.
- **FR-025**: Ranking и agent output MUST NOT изменять hiring status или создавать автоматический отказ.

#### Alternative vacancy matching

- **FR-026**: Alternative matcher MUST рассматривать только активные вакансии разрешённых грейдов.
- **FR-027**: Альтернативный match MUST содержать matched criteria, gaps, evidence references,
  compatibility status, fit value и explanation.
- **FR-028**: Eligibility в strong-candidate pool MUST вычисляться детерминированно по versioned
  минимальному порогу overall readiness и evidence coverage.
- **FR-029**: Не прошедший eligibility профиль MUST NOT получать опубликованные альтернативные
  рекомендации и MUST содержать explainable reason code.
- **FR-030**: Несовместимые competency versions MUST давать `manual_comparison_required`, а не
  искусственный общий score.

#### Integrity and restrictions

- **FR-031**: Integrity agent MAY создавать только `consistent`, `unverified_claim`,
  `contradiction_detected` или `manual_integrity_review` observations.
- **FR-032**: Integrity observation MUST ссылаться на обе стороны противоречия и MUST NOT называться
  доказательством лжи без внешнего подтверждения.
- **FR-033**: Только авторизованный человек MAY создать `verified_misrepresentation`, `restricted`
  или `blacklisted` decision.
- **FR-034**: Human restriction MUST быть append-only и содержать actor, reason, evidence, creation
  time, optional expiry и ссылку на superseded decision при пересмотре.
- **FR-035**: Активное человеческое ограничение MUST исключать профиль из strong-candidate pool,
  но MUST NOT переписывать исходные agent observations или interview scores.

#### Governance and privacy

- **FR-036**: Все выводы MUST разделять verified facts, source claims, agent observations,
  deterministic calculations и human decisions.
- **FR-037**: Внешность, пол, возраст, национальность, акцент, эмоции и voice confidence MUST NOT
  использоваться для scoring, ranking, matching или integrity decisions.
- **FR-038**: Candidate-facing projections MUST NOT содержать позиции других кандидатов, внутренние
  веса, integrity notes, ограничения или кадровые решения.
- **FR-039**: Тестовые и демонстрационные данные MUST быть synthetic и MUST NOT содержать PII.
- **FR-040**: Все смысловые agent stages — `resume_relevance`, `question_plan`,
  `answer_assessment`, `alternative_vacancy_match` и `integrity_check` — MUST выполняться LLM через
  валидируемый structured-output контракт; runtime MUST NOT подменять их эвристическим или
  детерминированным анализатором.

### Key Entities

- **AgentSession**: Изолированная сессия обработки одного кандидата для основной вакансии с
  закреплёнными input versions и текущим состоянием workflow.
- **SessionMemoryItem**: Версионированная ссылка на разрешённый входной или производный артефакт.
- **AgentOperation / AgentRun**: Идемпотентная операция и отдельные попытки её выполнения.
- **ResumeClaim**: Заявленный в резюме факт с происхождением и статусом проверки.
- **ExperienceMatch**: Связь фрагмента опыта с требованием вакансии или manager brief.
- **QuestionSelection**: Базовый или персональный вопрос с criterion и selection lineage.
- **ConfirmedAnswer**: Неизменяемый ответ, сохранённый до оценки.
- **CriterionObservation**: Evidence-based наблюдение по одному критерию и dimension.
- **CandidateProfile**: Детерминированный итог подтверждённых компетенций, покрытия и ограничений.
- **RankingSnapshot / RankingEntry**: Совместимая когорта и стабильная позиция кандидата.
- **AlternativeVacancyMatch**: Объяснимая связь профиля с другой активной вакансией.
- **IntegrityObservation**: Агентный флаг согласованности, не являющийся кадровым решением.
- **RestrictionDecision**: Отдельное append-only решение уполномоченного человека.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В 100% тестовых сессий все результаты трассируются до конкретных версий вакансии,
  резюме, manager brief, вопроса и ответа.
- **SC-002**: В тесте из 1 000 синтетических сессий отсутствует перенос данных между кандидатами или
  вакансиями.
- **SC-003**: 100% числовых criterion observations содержат точный evidence, а 100% случаев без
  evidence представлены как `insufficient_information/null`.
- **SC-004**: Повтор любого завершённого этапа с тем же ключом не создаёт дубликатов; после одного
  искусственного сбоя workflow продолжается с последней успешной контрольной точки.
- **SC-005**: Для одной совместимой когорты повторное построение ranking snapshot без изменения
  входов даёт тот же порядок кандидатов.
- **SC-006**: В синтетической выборке каждый alternative match содержит объяснимые совпадения и
  пробелы; ни один не прошедший eligibility профиль не попадает в strong-candidate pool.
- **SC-007**: Ни один agent output, включая `contradiction_detected`, не создаёт blacklist или
  автоматический кадровый отказ.
- **SC-008**: 100% ограничивающих решений имеют человеческого автора, основание, evidence и
  неизменяемую историю.
- **SC-009**: Recruiter может получить итоговый профиль, ranking и alternative matches менее чем за
  2 секунды после завершения асинхронных agent stages для когорты до 1 000 synthetic candidates.
- **SC-010**: На калибровочной выборке не менее 80% итоговых рекомендаций совпадают с независимым
  review рекрутёра и технического эксперта до использования системы в реальном отборе.

## Assumptions

- Текущий FastAPI backend, существующие invitation, vacancy, resume, manager brief и transcript
  workflows являются исходной платформой и сохраняют обратную совместимость.
- Пожелания менеджера влияют на систему только после явного утверждения; агент не создаёт
  отсутствующие требования.
- Базовые вопросы и критерии вакансии задаются утверждённой версией конфигурации; персонализация
  ограничена вопросами на проверку уже существующих claims и criteria.
- Одна шкала `signed_criterion_v1` используется для нового workflow; результаты старых шкал не
  смешиваются с ней.
- Минимальные пороги overall readiness, coverage и разрешённые соседние грейды являются
  версионированной политикой и настраиваются до формирования когорты.
- Cross-vacancy matching является рекомендацией рекрутёру и не создаёт новую заявку кандидата без
  человеческого действия и соответствующего согласия.
- Blacklist не является agent capability. Термин используется только для отдельного, аудируемого и
  пересматриваемого человеческого ограничения.
- Все пять смысловых агентов используют LLM. Детерминированный код применяется только для
  безопасности, валидации, агрегации, eligibility, ranking и применения человеческих решений.
