# Technical Research: Interview Platform Architecture POC

## Decision 1: Modular monolith with inward dependencies

**Decision**: Use domain, application, infrastructure, and web packages inside one deployable Python process.

**Rationale**: The POC needs visible architectural seams more than independent scaling. One process keeps local setup and tests fast while dependency inversion preserves replaceability of storage, media capture, and delivery mechanisms.

**Alternatives considered**:

- Separate frontend and API services: rejected for the POC because deployment and dependency overhead would not validate additional product risk.
- A single HTTP module with direct SQL: rejected because state and evidence rules would become coupled to transport and expensive to replace.
- Early microservices: rejected because current scale and team boundaries do not justify distributed failure modes.

## Decision 2: Standard-library WSGI and server-rendered UI

**Decision**: Use `wsgiref` for the local runner, a small explicit WSGI router, HTML generated by presenters, and progressive HTML forms with minimal browser scripting.

**Rationale**: This matches the repository's zero-dependency constraint, produces a genuinely runnable three-portal demo, and keeps the architectural focus on contracts and use cases rather than framework setup.

**Alternatives considered**:

- FastAPI plus a JavaScript SPA: strong future option, but adds two toolchains and masks the essential domain boundary in the first POC.
- CLI-only demonstration: rejected because separate candidate and manager interfaces are a direct requirement.

## Decision 3: SQLite behind separate repository ports

**Decision**: Persist interview state through one repository port and recruiter/manager review state through a second role-review port, backed by separate SQLite tables.

**Rationale**: SQLite provides transactional state changes and restart persistence with no external service. The port keeps PostgreSQL migration localized when concurrency or deployment needs grow.

**Alternatives considered**:

- In-memory dictionaries: simpler, but fail the resume-after-restart behavior and under-test persistence design.
- JSON files: human-readable, but awkward for atomic multi-entity updates and state queries.
- PostgreSQL now: production-capable, but unnecessary operational dependency for a local POC.

## Decision 4: Token candidate access and separate staff credentials

**Decision**: Give each candidate a high-entropy bearer token, store only its digest, and protect recruiter and manager capabilities with distinct runtime-configured secrets and API headers.

**Rationale**: This visibly separates all three roles without prematurely designing account lifecycle or SSO. Hash-at-rest limits damage from an accidental database disclosure, while different staff credentials make permission tests meaningful.

**Alternatives considered**:

- Email/password accounts for both roles: deferred because recovery, verification, and identity management are not the product hypothesis being tested.
- Unprotected manager demo route: rejected because it would violate the required authorization boundary and make later hardening harder.

## Decision 5: Media capture port with a text stub

**Decision**: Define a capture interface returning a capture kind and reference; use a text-answer adapter in the POC.

**Rationale**: Candidate progress and manager evidence can be exercised now while real upload, resumable chunks, object storage, transcription, and consent auditing remain replaceable edge concerns.

**Alternatives considered**:

- Browser webcam recording in the first slice: rejected because upload resilience and media retention would dominate the architecture before the portal workflow is validated.
- Pretending text is video: rejected; all UI and stored metadata explicitly label the adapter as a POC stub.

## Decision 6: Evidence-linked recruiter feedback and independent manager review

**Decision**: Require every recruiter review evidence item to reference a question/answer and excerpt, or use the explicit `insufficient_information` kind. Store candidate-visible text independently from internal notes, recruiter decision, assignment, and manager review.

**Rationale**: This enforces repository product principles at the domain boundary and prevents the UI or a future model adapter from silently inventing support.

**Alternatives considered**:

- Free-form unlinked feedback: rejected because it is not auditable.
- Numeric scoring in the POC: deferred until rubric versioning and evaluation design are implemented.

## Decision 7: Assignment is an authorization boundary

**Decision**: A manager list and direct lookup are both resolved through the recruiter assignment. Reassignment revokes old access and clears the stale current manager review.

**Rationale**: Hiding unassigned records only in the interface would leave an insecure direct-object path. Enforcing the check in the application service keeps web and future adapters consistent.

**Alternatives considered**:

- UI-only filtering: rejected because direct manager API calls could still disclose candidates.
- Full organization directory and RBAC service: deferred until the POC validates role workflows.
